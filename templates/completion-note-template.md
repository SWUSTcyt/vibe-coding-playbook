# 跟用户说话

每一次回复用户都适用。不限于 Issue 做完，不限于 PR 合并，也不限于有界面。

先说人话：这件事对当前工作意味着什么、为什么是这样、接下来要谁决定什么。用户看完还得问「这是什么意思」或「为什么做这一步」，就还没写完。用这个项目里的事写。记录里没有的原因就写「没有记下」，不补编。

短回复不必凑四个标题。意味着什么、为什么、接下来要谁决定什么，这三件里用得上的写，用不上的不写，不为凑数加句子。

阶段有了结果时写满下面四段，例如做完一块、检查跑完、计划定了、要用户做决定、合并代码。技术收据放在四段后面。PR 摘要里的完成说明用这四段，不另写一套。

## 1. 现在意味着什么

用这个产品或这项工作的人，现在多能做哪件事，或者这次说明让他知道什么。看不出差别就写看不出，并说清哪些没变。

## 2. 为什么

之前卡在哪，不做会怎样。记录里没有原因，就写「原因没有记在这次结果里」，不补编。

## 3. 变了什么、没变什么

什么变了、什么没变。涉及上线或操作时，写要不要重新部署、用户要不要重新做一遍。

## 4. 接下来

接下来和哪件事有关，要谁决定。没有就写没有。

## 技术收据

数字、命令、文件名和结论放在人话后面，不删。第一次出现的技术词，同一句里用半句白话说它是什么，不另做术语表。原文没解释的词，写「原文没解释」，不补编。

## 禁止

下面这些都不算讲明白：

- 只在合并时，或只在有界面时，才这样写。
- 只回复「已完成」「已合并」「测试通过」或「内部改动，无用户可感知变化」。
- 把编号、通过率、命令或文件名放在人话前面。
- 用某一次项目的收据当作规则本身。一次看不懂的回复只说明一种失败样子，不是全部。

不合格的样子：一上来是编号、命令、通过率或文件名，读完不知道这件事解决什么、为什么现在做、自己要不要做决定。
