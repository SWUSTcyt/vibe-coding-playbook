# 项目架构可见性（按需）

> 给 `plan-breakdown`、`verify-review` 用。命中下面的触发条件才读。单文件脚本、短期 spike、只改文案或不改职责边界的 Bug 不读。
> 总览模板：`templates/architecture-overview-template.md`。
> 分层「不该做什么」、按关注点剥离，仍看 `reference/service-refactor-guide.md`。本文不重复那一套，只补「人怎么找到代码」。

证据来自一个多能力项目的一轮结构整理（2026-11）。第二个不同技术栈回放之前，触发条件不是所有项目的硬门禁。

## 何时创建

命中任一，就在结构迁移之前先拆一个「地图与边界」Issue，用模板写总览：

- 已有两个及以上可独立感知的业务能力
- 同一业务核心接入多个平台、协议或连接器
- 准备跨目录、分层、模块化或兼容迁移
- 负责人能讲清业务，却说不清源码、状态和测试在哪
- 新需求经常被迫同时改接入、业务、配置或存储
- 审查发现说明、流程图、源码行为或能力状态互相矛盾
- 新的 Agent 要读很多文件才能判断从哪改

这个 Issue 至少包括：总览文档、能力到实现和测试的映射、索引入口、至少一条可证伪的边界、以及「不改变业务行为」时要回归的范围。不要塞进每个 Milestone。`PLAN.md` 只挂链接，不写架构正文。

## 何时只改一节

已有总览，并且这次改了业务入口、确认或失败顺序、模块位置或公共导入、连接器、或总览里写明的禁止依赖：只改受影响的章节。普通函数调整、内部重命名、不改变职责的重构，不改总览。

## 何时不做

- 单文件脚本、短期 spike、一次性实验
- 只有一个入口和一个业务模块的小工具
- 只改文案、局部样式，或不影响职责边界的 Bug
- 已有总览仍然准确

## 总览不做什么

不替代依赖扫描图、API 全文、PLAN、Spec 或 Issue。不把计划中的能力、模拟结果或只做了契约测试的能力写成已经上线。不规定语言或目录名。边界检查优先用该语言生态已有的依赖规则工具；本文不规定某一种语法分析器。
