## 合入前审查（2026-11-21）

审查模型 Claude Fable 5.2（高级档），只读，检查只在本地运行。编写用的模型以会话摘要的记录为准，审查者核实不了。结论：上面的验收项成立，另有 2 条 P1，先不合入。用户选择改掉 P1 和 P2，推送后再确认合并。审查后的修改由审查模型来做，没有再独立审查一遍。

- P1（已改）：初版把用户贴出的收工说明原样抄进了本文件，带另一个项目的人员称呼、产品事项、内部 PR 号和提交编号，而本仓库是公开的，内容已随分支推到远端。改为去掉细节后的改写，并按用户选择重写了提交。旧提交在托管平台上凭编号可能还能打开一段时间。
- P1（已改）：范围扩大那一轮没有等确认，会话摘要却写「绕过确认 0 次」「范围没变」，验收表标题写成全部来自已确认的计划。已改实，见上面「同日范围修正（补记）」。
- P2（已改）：已有 `AGENTS.md` 的项目重装会跳过这份文件（临时目录实测），那一条到不了老项目。README 和 CHANGELOG 写明要手工加。
- P2（已改）：模板原来要求短回复「三件不能空」，会逼着凑数。改为用得上的写，用不上的不写。
- P2（已改）：CHANGELOG 的标题和产出、会话摘要的提交状态、本文件里「三种」「反例」等过时说法，以及没记发布授权。
- P3（没改，用户选的是改 P1 和 P2）：`pr-summary-template` 前两段的标题和完成说明模板的不一样；模板文件名是 `completion-note-template`，内容已是通用规则；会话摘要没写编写模型的档位。

## 一个例子，不是规则本身

下面是去掉项目细节之后的改写，不是原话。它只说明一种看不懂：技术清单放在前面，没写意味着什么、为什么现在做。提问、中途进度、计划说明看不懂，不在这个例子里。所以它不定义规则，只留在本文件，不抄进分发的模板。

看不懂的样子：

> 已经全部收口并合入 main。
>
> - PR 已合并，merge SHA：（提交编号）
> - 独立 L2：P0/P1/P2/P3 均为 0
> - PR 与 main CI 均全绿
> - main 回归：（若干）passed，（若干）skipped
> - 覆盖率：（百分比），通过 80% 门槛
>
> 已经落地的优化包括：（一串测试和检查方面的技术名词）。
>
> 当前最慢的仍是某一类全量门禁，约若干分钟。先观察后续几个 PR，再决定是否优化，暂不夸大节省比例。
>
> 本次只是测试基础设施合并，没有生产部署，也没有用户功能需要重新上线。接下来可以开始规划下一项产品优化。

同样的事实，讲明白的样子。只用上面已有的内容，不补编：

用这个产品的人，这次多做不了新的事。这次合并的是测试基础设施，没有生产部署，也没有用户功能需要重新上线。页面和具体操作有没有变，原文没写。

为什么现在做这一步：原文只列了已经落地的几项测试和检查上的优化，没有说之前卡在哪、不做会怎样。原因没有记在这次结果里。

变了什么、没变什么：那几项优化进了主干，也就是大家共用的那条代码线。最慢的一类全量检查还是要跑若干分钟，先看后面几个 PR 再决定要不要优化，并且先不夸大能省多少。没有生产部署，用户不需要重新操作。

接下来：可以开始规划下一项产品优化。原文把它放在这次合并之后，没有写这两件事互相挡住。

技术收据：

- PR 已合并，附了提交编号，也就是这次合并在版本历史上的编号。
- 独立 L2：P0 到 P3 都是 0。L2 原文没解释，不补编。
- PR 和主干上的 CI 都全绿。CI 是自动跑的一组检查。
- 主干上的回归通过。回归是把已有的检查再跑一遍。
- 覆盖率过了 80% 这道线。覆盖率是测试执行到的代码比例。

## 限度

这是写给 Agent 的文字规则，不是拦截，也没有在项目里试用过。`AGENTS.md` 每次开工会读到，但项目里已经有这份文件时，安装不会覆盖，要手工把「跟用户说话」这一条加进项目自己的 `AGENTS.md`；没加的话，只有打开某个 Skill 时才看得到这句。8 个 Skill 会随安装更新。别的项目要等用户点名后再安装。
